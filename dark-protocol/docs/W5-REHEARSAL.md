## Initialize — FAILED: W5 FINDING (Critical, deployment-blocking)

The driver's initialize send was blocked at RPC preflight
simulation. Follow-up simulations of the exact instruction:

| CU limit | result | units consumed |
|---|---|---|
| 1,000,000 | `ProgramFailedToComplete` — "exceeded CUs meter at BPF instruction" | 1,000,000 |
| 1,200,000 | `ProgramFailedToComplete` | 1,200,000 |
| 1,400,000 (protocol max) | `ProgramFailedToComplete` | 1,400,000 |

**Root cause (from the source):** `initialize` performs **60
on-chain Poseidon hashes** — `Frontier::new()` computes
`zero_chain(20)` (20 hashes), and `Frontier::root()` computes
`zero_chain(20)` *again* (20) plus a 20-level fold (20). At the
1.4M cap this prices the SBF Poseidon path at **> ~23K CU per hash**
(light-poseidon parameters materialized on the heap; the arithmetic
is BN254 Poseidon in unoptimized SBF bytecode). Host test suites
cannot see this — there is no CU metering off-chain, and the SBF
build was previously verified for stack frames and determinism,
never executed.

**Blast radius:** `deposit` runs 41 hashes (1 leaf binding +
`insert`'s zero_chain 20 + fold 20) — likely also at/over the cap;
it cannot be tested until initialize lands. `withdraw` does not
recompute the zero chain and may fit, but is unreachable. As
compiled, **the pool can never be initialized in a single
transaction, on any cluster** — this is not a devnet-only problem.

**Not attempted (behavior freeze):** no program-logic change was
made. Candidate fix directions for a follow-on work order (dev's
call): precompute the 21 zero-chain values as constants (they are
fixed for depth 20 — the same rodata treatment the frame fix gave
the Poseidon parameters), which removes 40 of initialize's 60
hashes and 20 of deposit's 41; and/or evaluate the CU cost of the
Poseidon permutation itself under SBF with an eye to a leaner
implementation. After any fix: rebuild, re-verify determinism,
re-run host suites, redeploy (upgrade) and resume this rehearsal
from initialize.

Pool PDA and Vault PDA confirmed **absent** on-chain after the
attempts — no partial state exists.

## The fix

- **Zero-chain constants** (`programs/dark-protocol/src/zero_chain.rs`,
  new): the 21 depth-20 zero values z[0..=20], generated mechanically
  by iterating the defining recurrence with the program's own
  `poseidon2` host-side and emitting `BigInteger256` limb quads (the
  `poseidon_params.rs` representation) via a temporary generator test
  that was removed once the table existed. No hand transcription.
  `merkle::zero_chain` now serves depths ≤ 20 from the table (the
  chain is prefix-consistent) and extends past it by the recurrence.
- **Fold short-circuit** (`merkle::combine`, used by `Frontier::root`
  and `Frontier::insert` — the only two fold sites): if both children
  of a fold step are byte-exactly the level's zero constant, the
  parent is by definition the next zero constant — a table lookup
  with a bit-identical result. Byte-exactness against the constants
  means it can only fire on the constant pair itself. This is what
  takes the empty tree's root fold to zero hashes.
- **Hash counts (from source), before → after:** initialize 60 → 0;
  deposit 41 → 21 (1 bound-leaf + 20 insert folds; the zero-chain
  recomputation is gone); withdraw 1 → 1 (recipient binding;
  unchanged — it never touched the zero chain).

# Poseidon-cost track (2026-11-17, later) — deposit cured; rehearsal completed

Dev-authorized follow-on to the section above: lab-measure the
per-hash cost, implement the fastest byte-identical route, upgrade,
and resume the rehearsal at deposit. The complete cost record —
decomposition, every route's numbers and verdict, the byte-identity
evidence, and forward guidance for W8 — is
`dark-protocol/docs/POSEIDON-COST.md`. This section is the
rehearsal-side record.

## Lab summary (devnet-measured, real SBF execution)

- `circom2_parameters()` construction alone: **625,961 CU**.
- One permutation with parameters pre-built: **> 773,889 CU**
  (bound: a params-once instruction aborts at the 1,399,850 cap).
- One hash on the old path (construction + permutation, paid per
  call): **> 1,399,850 CU** — deposit died on its *first* hash, not
  its last. Both recorded hypotheses were true, each independently
  fatal.
- Route A (parameters threaded per instruction): dead by the same
  measurement (projected deposit > 16.9M CU).
- **Route B (`sol_poseidon` syscall via `solana-poseidon`):
  ~819 CU/hash marginal** (n = 100 chained: 82,224 CU total).
  Byte-identity vs the old implementation proven on devnet before
  any program change: KAT, the full depth-20 zero chain, the true
  modulus−1 boundary pairs, and a 206-case differential (200
  randomized canonical pairs) — **206/206 match, 0 mismatches**;
  inputs ≥ Fr modulus rejected by both implementations.
- Groth16 verify of the sample proof (real VK, handler's exact
  sequence): **106,393 CU**, valid.
- Lab method note: the local test-validator cannot run in this
  sandbox (Agave 4.2 panics on its io_uring assertion) and the
  program-test tree would not resolve from the local registry
  caches, so the lab ran as two throwaway programs deployed to
  devnet and metered by simulation. Both lab programs were closed
  afterward and their rent reclaimed to the deployer
  (0.59141868 + 0.0939038 SOL).

## Fix and upgrade

- Change: `poseidon2` body only → `solana_poseidon::hashv`
  (Bn254X5, big-endian), same error mapping; `Cargo.toml` +
