# W8-B — Shielded transfer circuit (follow-on work order, NOT part of the core transplant)

**Status: design only. In the merged v1, `transfer` is a fail-closed
stub (`TransferNotEnabled`) — the handler exists so the instruction
errors explicitly, never silently succeeds, never moves funds, never
consumes a nullifier.**

## Why a new circuit (not a handler change)

The withdraw circuit's public inputs `[root, nf, recipient, amount]`
cannot express hidden-value conservation between one input note and two
output notes: the amounts are exactly what a transfer must hide. Any
"transfer" built on the withdraw VK would either leak amounts or skip
conservation — the two failure modes the rewrite exists to eliminate.

## Circuit sketch (1-in / 2-out, full conservation)

- Private: sk, input note (owner_id, value_in, blinding_in), leaf index +
  Merkle path, output notes (owner_id1/2 or recipient owner ids,
  value1, value2, blinding1/2).
- Computed in-circuit: nk, owner_id, cm_in, **bound leaf
  Poseidon(cm_in, value_in)** (NEW-1 binding applies to spends of every
  kind), nf = Poseidon(nk, leaf_index), cm1, cm2.
- Constraints: Merkle membership of the bound leaf under the public
  root; cm_in opens correctly; **value_in == value1 + value2** with
  range checks on all three (u64 range, matching the program's amount
  encoding); cm1/cm2 well-formed.
- Public inputs (proposed, order fixed): `[root, nf, cm1, cm2]`.
  Outputs are inserted as bound leaves by the program:
  `Poseidon(cm1, value1)` — wait: the program cannot compute output
  bound leaves without knowing value1/value2, which are hidden. **Open
  design point:** output leaf binding needs the values visible to the
  program or a different binding. Options: (i) outputs carry their own
  deposit-style binding via a second-level commitment the circuit proves
  consistent (leaf_i = Poseidon(cm_i, value_i) computed in-circuit and
  made public as `leaf1, leaf2` public outputs — the program inserts
  exactly those, and membership proofs later open them the same way
  withdraw does); (ii) make value1/value2 public (leaks the split —
  rejected). Option (i) is the coherent extension of NEW-1: public
  inputs become `[root, nf, leaf1, leaf2]` and cm1/cm2 stay private
  (the program never needs them: it inserts leaves, and note delivery to
  recipients is the client's encryption layer, as in v1). This also
  means deposit and transfer produce indistinguishable leaf insertions.
- Ceremony: new circuit ⇒ new phase-2 (reuse the ptau if constraint
  count fits 2^14, else size up); VK generated by the same export
  pipeline, never hand-typed.

## Program changes
`transfer` handler adopts the withdraw gate order: root-in-ring →
verify (transfer VK) → nullifier marker `init` → insert leaf1, leaf2 →
totals unchanged (conservation means totals don't move; assert
`total_deposited - total_withdrawn` invariant untouched). Two frontier
inserts in one instruction — frontier code already supports sequential
inserts (root ring pushes the final root; intermediate root also pushed
is acceptable but must be a conscious choice, documented).

## Client changes
This work order **closes REAUDIT NEW-2**: client-lib's
`buildSpendInputs`/`createSpendProof` were written against a transfer
shape before the circuit existed. Rebuild them against the final
public-input layout above; the withdraw path (`buildWithdrawInputs`
equivalent) stays as the proven v1 flow.

## Tests (mirror the v1 bar)
Honest transfer proves + verifies; conservation attacks fail (value1 +
value2 > value_in cannot produce a witness); drain regression (input
note deposited at 1 lamport cannot transfer out more); double-spend via
replay aborts at the marker; tampered leaf1/leaf2/root/nf rejected;
program state-machine tests for the two-insert transition incl. root
ring behavior.
