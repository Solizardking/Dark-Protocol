02Why formal verification, and why here

Privacy systems fail quietly. A public ledger at least shows you the theft; a shielded pool can hide it. Three layers of our stack need more than tests.

Zero-knowledge & confidential-state soundness

When amounts and owners are hidden, the program's own bookkeeping is the only thing standing between a pool and a drain. We have already fixed one bug of exactly this kind (tracked as NEW-1): a deposit's amount was not bound to the note it created, so a 1-lamport deposit could have been dressed up to drain the pool. A proof that the leaf is always Poseidon(commitment, amount), for the amount actually transferred closes that whole class of bug for good, which no test suite can do.

TEE attestation gating logic

Confidential compute is only as strong as the code that decides "this enclave is trusted". Umbra unlocks sends only when verification passes with a fresh nonce; our agent SDK checks measurements, signatures, allow-lists, and quote age. While writing this scope we found that a hardware-imported quote's measurement is derived differently from the one the verifier recomputes, so the two paths disagree. Gate logic like this should be specified and proved, not eyeballed.

On-chain program invariants

Conservation of lamports, no admin backdoor, a rejected proof never burns a note, honest withdrawals always go through, and an append-only root history. These are universal statements over every sequence of instructions, so only a proof can settle them.

04The ask

Our first run was funded by a 500-credit signup grant. It used all of it in about two hours and ended with all seven properties unresolved: none proved, none refuted, no counterexamples. The verifier didn't find our code wrong. It ran out of fuel partway through.

Solana Foundation: fund formal-verification credits for private Solana

  1. Phase 1: finish the pool. Resume the existing Aristotle project and complete the seven pool properties, starting with deposit binding and conservation of funds. From the burn rate we observed, we estimate this at roughly $1,000–$2,000 in credits.
  2. Phase 2: the circuit and the gate. Under-constraint analysis of the withdraw circuit, and a formal model of the Umbra TEE gate and attestation verifiers.
  3. Phase 3: settlement. Start the order-book pilot that's already packaged.

Credits paid directly to a verification provider, or funding earmarked for verification, both work for us. We'll publish a costed plan for Phases 2–3 before any spend.

05What the ecosystem gets back

  • Open specs and proofs. Every property statement, Lean artifact and verifier output, published in a public repository.
  • Public reports. Each property is reported as proved, refuted with its counterexample (and our fix), or unresolved, with the verification boundary stated. Results get published whether they're good or bad.
  • Reusable verified primitives. Amount-bound Poseidon leaves, nullifier-PDA one-time spends, append-only root history, and an attestation-gated RPC pattern. Any Solana privacy or confidential-compute team can reuse them.
  • A worked example. A real-world case study of formally verifying a ZK-adjacent Solana program, including what it cost.

07What this page does not claim

Honest limits, on purpose

  • No property has been formally proved yet. "Formal verification" here means the work we've specified and started, not a result.
  • The Solana Foundation has not funded, endorsed or reviewed this work. This page is a request.
  • Helius and Crossmint are integrations we're building. They have not endorsed us, and we have no partnership with either.
  • Dark Protocol runs on devnet. Mainnet waits for the MPC ceremony and the verification results.
  • Formal verification proves stated properties under stated assumptions, such as the hash function and the Groth16 verifier being treated as trusted. It isn't a guarantee of everything.
